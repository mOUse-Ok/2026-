LLM Runtime / Linux VM 语义工作集管理
决赛答辩稿初稿（约 13 分钟）

使用原则
1. 只陈述已经完成的实现和已有实验数据。
2. 场景 B 的新版 12 GiB Router 预取实验，在拿到满足“输出一致且 hint issued > 0”的三次结果前，不宣称性能收益。
3. 不把 MADV_WILLNEED、MADV_COLD 或 MADV_DONTNEED 的成功返回解释为页必然驻留、页必然释放或性能必然提升。

第 1 页：封面（0:00—0:30）
各位评委老师好。我们汇报的项目是“LLM Runtime / Linux VM 语义工作集管理”。赛题关注内存受限环境下的大模型推理优化。我们的核心目标不是重新实现模型算法，而是让操作系统能够获得 LLM Runtime 中真实的 Expert 需求语义，并据此进行可审计的内存管理。

第 2 页：问题背景（0:30—1:15）
本项目使用 Qwen3.5-35B-A3B Q3_K_M 模型。模型文件约 15.23 GiB，而已有基准使用 7040 MiB 的 cgroup 上限。模型可以通过 mmap 建立虚拟地址映射，但这不表示全部权重页都能常驻内存。内存受限时，真正的限制是可驻留的工作集，而不是虚拟地址空间。

第 3 页：系统后果（1:15—1:50）
在 7040 MiB 冷缓存基线中，平均每次运行约有 80 万次 Major Fault。其含义是：后续访问到被回收的文件页时，需要重新读取。它会增加推理关键路径等待。这里我们只报告 Major Fault 的计数，不把每一次 Major Fault 直接归因到某一个 Expert。

第 4、5 页：为什么关注 MoE Expert（1:50—2:35）
模型中约 85.19% 的 tensor bytes 来自 Routed Experts。但每个 MoE 层有 256 个 Expert，每个 token 每层只激活 8 个。也就是说，模型容量很大，而一次计算的即时需求是稀疏且有明确语义的。这为按 Expert Slice 管理内存提供了基础。

第 6 页：核心问题（2:35—3:15）
Linux 虚拟内存看到的是地址、文件偏移、页面状态和压力指标。LLM Runtime 看到的是 token、层、Router 选出的 Expert 和后续需求。两侧信息不能直接对应。我们的工作是建立这条对应关系：让 Runtime 的 Expert 语义能够定位到 Linux 中的文件映射地址范围。

第 7 页：Memory Object（3:15—4:00）
我们将一个 Expert Slice 抽象为 Semantic Memory Object。它的身份由 layer、expert 和 tensor 构成；它保存地址范围、需求状态、in-flight hint、Working Set 状态和 logical first-use 等信息。它是用户态管理对象，不是 Linux 内核对象，也不等同于物理页所有权。

第 8、9 页：端到端语义通路（4:00—4:50）
具体过程是：Qwen 原生 Router 输出 Expert ID 和 score；Registry 将其转换为 GGUF mmap 中的 Slice 地址和长度；系统据此建立任务，并在允许时向 Linux 发出 MADV_WILLNEED。我们直接复用原生 Router，不构造模型外部预测器。这个通路把“模型将使用哪个 Expert”转换为“操作系统应关注哪个文件映射范围”。

第 10 页：异步与安全门控（4:50—5:30）
OS hint 不在 Router 线程同步执行。任务进入异步队列后，还会经历压力、价值和语义过期检查。任务可以被拒绝或取消。这样做的目的不是保证每个 hint 都发出，而是在系统压力较高或任务已经失效时不增加无效工作。

第 11 页：生命周期闭环（5:30—6:15）
系统还跟踪 demand、first-use 和 layer completion。已有 N=5 生命周期实验中，102,222 个 demand、activation、completion 与 slot acquire/release 数量全部闭合，结束时 pending 和 active 均为 0，invariant violations 为 0。该实验验证状态语义正确；Lifecycle ON 的 wall time 增加 13.71%，因此不能把它描述为性能优化。

第 12 页：Semantic Working Set 与安全回收（6:15—7:05）
Working Set 管理的是语义容量，而不是伪装成物理 RSS 上限。对象有未完成 demand 或正在使用时不能回收；只有已经被语义淘汰、没有 pending/active/in-flight hint、经过 grace steps、且完整位于文件映射内部的 Slice，才允许作为 DONTNEED 候选。每个 Decode step 还有 64 MiB 全局回收上限。

第 13 页：观测成本与控制模式（7:05—7:45）
完整观测会带来成本。最小 Trace 相对 Plain 的 wall time 成本约为 3.66%。因此我们区分 Evidence Trace 和 Runtime Control：分析访存行为时保留完整事件；运行管理和性能测试时关闭 Tensor、KV、Expert 原始事件等详细写出，只保留 Router 解析、必要状态和最终汇总。关闭事件写出不等于关闭管理状态。

第 14 页：历史预取负结果（7:45—8:30）
在 7040 MiB、N=5+5 的历史冷缓存 A/B 中，Router-driven prefetch 的 decode average 增加 12.24%，Major Fault 仅下降 0.50%。这说明 Router 到 OS hint 的通路可以运行，但并不自动带来加速。我们保留这一负结果，并据此收紧预取规模、Trace 开销和实验边界。

第 15 页：场景 A，内存极紧时的完成性结果（8:30—9:35）
最新场景 A 使用 384 MiB cgroup、无 swap、独立 scope。Plain llama.cpp 使用 F16 KV、ctx 2048、ubatch 512，35.15 秒后被 cgroup OOM kill。survival_static 使用启动期的低内存模板后完成，耗时 130.89 秒。survival_reclaim 在同一模板上启用受限 DONTNEED，也完成，耗时 164.86 秒，发出 2,240 次 DONTNEED。两个成功组输出 hash 一致。

这说明：启动期配置模板使系统能在 Plain 无法完成的上限下运行；受限 DONTNEED 的安全路径真实执行。reclaim 当前更慢，因此我们不把它描述为加速。

第 16 页：场景 B，内存较宽松但未完全驻留（9:35—10:35）
原先 20 GiB 的批量预加载实验不合适：模型加载后大部分模型页已驻留，Major Fault 为 0，预算也拒绝了批量预加载。因此新版场景 B 固定为 12 GiB：基线可以完成，但完整模型不能长期驻留；performance 组每层只对 Router 选中的 1 个 Expert 发 hint，基础预算为 64 MiB。

新版实验需要同一持久 llama-server 内比较 controller off 与 expert_prefetch，并报告输出 hash、hint issued、TTFT、后续 decode p95 和 Major Fault。只有 hint issued 大于 0 且输出一致时，才比较性能。若本次答辩前没有满足条件的三次重复数据，此页只展示设计与验证条件，不展示性能收益。

第 17 页：相关工作与差异（10:35—11:15）
已有 MoE 工作多数研究 CPU 与 GPU 或存储与设备内存之间的 Expert cache。我们的对象不同：GGUF 文件映射权重与 Linux Page Cache。我们的贡献不是宣称发明 Expert 预测，而是把原生 Router 语义映射到 OS 可操作的文件映射范围，并用生命周期、工作集和实验约束管理该过程。

第 18 页：证据边界（11:15—12:00）
本项目将正确性、机制行为、观测成本和性能结果分开报告。已经证明的包括 Router 到 Slice 的映射、任务和生命周期闭环、Working Set 行为、场景 A 的完成性收益以及 Trace 的成本。未证明的包括稳定的端到端 prefetch 加速、COLD 的净收益和 Runtime Rescue 的因果收益。

第 19 页：总结（12:00—13:00）
总结三点。
第一，我们在 llama.cpp CPU/MoE 路径中建立了 Runtime 到 Linux VM 的语义通路。
第二，我们将 Expert Slice 作为可管理、可审计的 Memory Object，并实现异步 hint、生命周期、Working Set 和安全回收。
第三，场景 A 已证明系统可在 Plain OOM 的 384 MiB 上限下完成推理；场景 B 已重新设计为 12 GiB 的小粒度 Router 预取验证，严格以实际 hint 与重复结果为准。

我们的结论不是“任意预取都会加速”，而是：操作系统可以获得并使用 LLM Runtime 的 Expert 语义；策略收益必须通过受控实验验证。谢谢各位评委老师。

高频提问准备
问：为什么不直接让 llama.cpp 自己管理？
答：llama.cpp 知道 Router 结果，但 Linux VM 决定文件页驻留和回收。项目的工作是把两者打通，并保留 cgroup、PSI、refault 等 OS 侧约束。

问：DONTNEED 成功是否代表内存一定降低？
答：不是。它只是 Linux advice。我们同时记录 cgroup 指标和后续 readmission，不由成功返回推导物理回收或性能收益。

问：为什么场景 A 的 reclaim 更慢还要保留？
答：它证明了受限回收路径的安全执行和完成性；结果同时说明该参数下没有速度收益。保留负结果可以避免不成立的性能结论。

问：场景 B 为什么改为 12 GiB？
答：已有内存扫描显示，16 GiB 时模型页接近全部驻留、Major Fault 接近零；12 GiB 时基线可完成但仍有明显缺页，是更适合验证小粒度预取的档位。

问：如何保证场景 B 的结果可信？
答：同一模型、同一 KV 和服务配置、独立 cgroup、冷缓存准备、持久 server、至少三次重复；输出 hash 一致且 performance 实际发出 hint 是比较性能的前提。
